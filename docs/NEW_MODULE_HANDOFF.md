# Хендофф: миграция модуля LifeOS (`meals` / `purchases` / `cosplays`)

Эту инструкцию получает бот, которому поручили перевести ОДИН модуль с localStorage
на общий backend. **Сначала прочитай `docs/ARCHITECTURE.md`.**

Репозиторий публичный: `git clone https://github.com/hasubandosan/organizz.git`.
Исходники модуля: `legacy-source/<module>/`. Образец уже мигрированного модуля: `frontend/projects/`.

**Категории, теги и связи между модулями — ОБЯЗАТЕЛЬНО прочитай `docs/TAGS_AND_REFS.md`.**
Своих тегов/категорий/зон в модуле не заводить: системные и личные теги берутся через
`DB.getTagOptions(<слаг>)`, в записях хранятся только `tagIds`.

## Что уже сделано за тебя (backend)
Схемы БД, роуты `/<module>`, регистрация в реестре и миграция для `meals`, `purchases`,
`cosplays` уже есть в `main`. **Backend тебе трогать не нужно.** Твоя зона — только фронтенд.

## Твои границы
**Можно создавать/менять:** только `frontend/<module>/`.

**Нельзя трогать (общие файлы — только через человека/архитектора):**
`frontend/core/*`, `frontend/hub/*`, `frontend/login/*`, `frontend/projects/*`,
всё в `backend/`, `docs/`, `netlify.toml`, чужие модули.
Нужна правка общего файла — не делай её, а опиши в отчёте, что и почему.

## Шаги

1. `cp -r legacy-source/<module> frontend/<module>` (если в модуле есть свой `db.js`/`sw.js`/
   `manifest.json` — см. «Особые случаи» ниже).
2. В `frontend/<module>/index.html` (и других страницах модуля) подключи общее ядро так же,
   как `frontend/projects/index.html`:
   ```html
   <link rel="stylesheet" href="../core/styles.css">
   <script>window.LIFEOS_APP_SLUG = '<module>';</script>   <!-- ОБЯЗАТЕЛЬНО, до db.js -->
   <script src="../core/db.js"></script>
   <script src="../core/ui.js"></script>
   ```
   Без строки со слагом модуль будет писать данные в `projects`.
3. Данные — только через `DB.*` (create/update/getById/getAll/query/delete...). Прямые
   обращения к `localStorage` для данных модуля запрещены (`grep -rn localStorage frontend/<module>/`).
   Исключения: чисто локальные настройки интерфейса (тема, последняя вкладка).
4. Картинки — только `DB.saveImage()` / `DB.getImage()`, в записях храни `id` картинки.
   Не клади base64 в поля записей.
5. Ссылки между модулями — относительные (`../hub/`, `../projects/`), не абсолютные.
6. Проверка без деплоя: `cd frontend && npx serve .` и открыть `http://localhost:3000/<module>/`.
   Вход на локальном сервере не заработает без настроенного CORS, поэтому основная проверка
   — после мержа и деплоя на Netlify (автоматически), её делает человек. Сам прогоняй:
   `node --check` по всем `.js`, поиск обращений к `localStorage`, ручной обход кода на
   предмет сломанных путей `../core/`.

## Особые случаи
- **У модуля свой `db.js`/хранилище (`meals`):** не удаляй сразу. Сначала составь короткий
  план: какие у модуля коллекции, какие функции хранилища он вызывает, как их замапить на
  `DB.*`. Пришли план человеку и дождись ответа, прежде чем писать код.
- **PWA (`sw.js`, `manifest.json`):** service worker может закэшировать старую версию.
  Не удаляй, но проверь пути и укажи в отчёте, нужен ли он.

## Как сдать работу
1. Работай в ветке `module/<module>` от свежего `origin/main`.
2. Итог — один коммит или серия, затем `git format-patch origin/main --stdout > <module>.patch`.
   У тебя, скорее всего, нет прав на push — отдай человеку файл патча и команды применения
   (человек работает в Windows PowerShell и плохо знаком с git: давай команды целиком, по шагам).
3. Перед выдачей патча проверь, что он применяется к свежему `main`: `git apply --check`.

## Отчёт человеку (коротко, без воды)
- Какие коллекции мигрированы (`entity_type`), как устроены записи, что нужно хабу
  (например, для виджетов — какие поля/статусы).
- Места, где модуль обращался к `localStorage` напрямую.
- Что не удалось проверить без деплоя.
- Что нужно поправить в общих файлах (если нужно) — список конкретных правок.
